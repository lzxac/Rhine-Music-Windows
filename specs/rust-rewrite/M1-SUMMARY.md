# Rust 重构 · M1 阶段总结

> 这是一份**给未来的自己看**的阶段收口文档：几个月后回来，能一眼看懂"当时验证了什么、结论如何、现在停在哪"。
> 技术细节不在这里：基线见 `specs/rust-rewrite/M0-baseline.md`，B2 实测见 `specs/rust-rewrite/M1-B2-result.md`。

## 1. 一句话结论

**假设成立，实验成功。** 把画面渲染从 WebView2/Chromium 换成原生（Rust）之后，原先吃不到的那块 GPU 开销被吃掉了：静止时 GPU 从 33.5% 降到 **0%**，内存从约 1GB 降到 **168MB**，启动快 **57%**。

## 2. M1 做了什么（每项一行）

- **M0**：冻结"重构前"的基线——性能数字、截图集、功能清单。
- **B1**：用 Rust 写一个空窗口程序，确认这台机器能编译、能运行、能关闭原生窗口。
- **B2**：用 Rust 把 3D 专辑货架画出来，并测 GPU、内存、启动三项指标。

## 3. 关键数字对比

| 指标 | 重构前（dev.11） | M0 门槛 | Rust B2 | 结论 |
|---|---|---|---|---|
| 静止时 GPU 占用 | 33.5%（优化后；优化前 88%） | ≤ 10% | **0%** | 通过 |
| 内存占用 | 约 1,050 MB | ≤ 400 MB | **168 MB** | 通过 |
| 冷启动到画面可见 | 3,099 ms | ≤ 2,169 ms | **1,338 ms** | 通过（快 57%） |
| 满速重绘时 GPU | 33.5%（与静止几乎相同 → 被"地板"卡住） | 未设门槛 | **22.7%** | 低于原栈静止值 |

## 4. 核心发现（一行一条）

- **WebView2/Chromium 的"合成地板"确实存在**：约 15–20 个百分点，不随帧率变化；原生渲染能吃掉它——这是换渲染层最实在的收益。
- 原生"满速重绘"（22.7%）已经**低于**原栈"静止"（33.5%）：原栈的下限比原生的满速还高。
- 这台电脑**没有 Visual Studio / MSVC**，Rust 只能用 GNU 目标；GNU 目标还需额外安装 WinLibs（提供汇编器）才能编译通过。
- 原生形态极简：**单个 22MB 可执行文件**、不依赖 WebView2 运行时、进程只有 1–2 个（原栈是启动器 + 多个浏览器子进程）。
- 现有 3D 素材**没有障碍**：现成的模型文件可被 Rust 直接读取，几何数据与现版吻合（顶点数、三角面数、包围盒都对得上）。

## 5. 已知局限（一行一条）

- **视觉 1:1 未验证**：B2 只画了货架本身；现版画面还包含地面、雾、封面贴图、后处理等，因此视觉对比**未匹配**（相似度为负）。这属于后续阶段的范围。
- **满帧负载未测**：只测了"静止"和"满速重绘"两种状态，未测切换专辑、加载封面等重负载。
- **只载入了 1 个模型**：现有 3 个 3D 素材中另外 2 个未载入。
- 未做：交互、动画、音频、曲库、界面、打包（均为 B2 范围外）。

## 8. 下一步选项（只列选项，由你决定）

- **启动 M2**：需要充足预算 + 明确范围（M2 具体做什么需另行确认）。

## 9. 未决问题（留给未来决策）

- **M2 先换哪一块**：先换"本地服务"（用户无感、风险低），还是先换"界面/渲染"（收益大、工期长）？
- **最终形态**：全量 Rust，还是"核心 Rust + 服务/工具链保留 Node"？
